- 路径：`D:\GitWork\MiaoSpritesPackage\local-role`
- **6746 对 png+plist，完全平铺无子目录**，总计 1.4 GB（png 1.37 GB / plist 28.6 MB）

```

```

- `views/action_diff_panel.py::_direction_of` 取父目录名，方向藏在文件名里会失效

## 实施：图集更新功能落地（用户澄清需求后）

### 需求澄清（重要，方向性变更）
用户明确：**不做切帧动画对比**。因为已打成单张图集，本就不存在动画效果，
只需求「同名单图对比 → 差异化 → 挑选替换」，复用现有【差异清单】，
避免手动复制粘贴 6746 个文件。

### 实现方案（传输内核零改动）
新增 4 个文件 + 修改 7 个文件，`git diff --stat`：+240/-12（不含新增文件）

**新增：**
- `utils/atlas_naming.py` — 图集命名解析器
- `services/atlas_scan_service.py` — 图集目录扫描（平铺→虚拟动作树）
- `adapters/atlas_folder_adapter.py` — `LayoutAwareFolderAdapter` 自动识别布局
- `tests/test_atlas_support.py` — 32 个图集专项测试

**修改：**
- `models/tree_node.py` — `is_previewable` 放行 atlas
- `services/compare_service.py` — `_resolve_status` 支持 atlas + size 兜底
- `services/action_diff_service.py` — 新增 `_collect_atlas_file_diffs` 分支
- `services/preview_service.py` — 新增 `_build_atlas_preview`（整图不切帧）
- `services/refresh_service.py` — 改用 `LayoutAwareFolderAdapter`
- `services/transfer_service.py` — 新增 `_expand_atlas_pairs` 成对补齐
- `views/action_diff_panel.py` — `_direction_of` / `_atlas_columns` / ROLE_SEARCH

### 关键设计决策

**1. 一图集 = 一个动作条目**
atlas 节点的 `node_type="atlas"`，`frame_files=[png, plist]`，
复用现有 CompareService / ActionDiffService / 差异清单 / 传输流程。

**2. 命名解析必须用「后缀剥离」而非「按 _ 切段」**
踩过的坑：`ride_idle` 含下划线，按 `_` 切会碎成 `ride`+`idle`；
`ride_back_N_ride_run` 的方向段夹在复合部件中间。
最终方案：从右向左剥离「最长动作后缀 → 最长方向后缀」，剩余 `partition("_")` 拆角色ID/部件。
全量回归：6745/6746 解析成功，仅 `50105101.png` 裸名降级（不丢文件）。

**3. 摘要用「文件名+字节数」而非内容哈希（性能关键）**
实测全量内容哈希 6746 条 = **15 秒**；改为 size 型摘要后 **0.5 秒**（30 倍）。
- 刻意 **不含 mtime**：SVN 检出/复制会重写时间戳，会造成大量假差异
- 兜底：差异服务对 `status=="same"` 的条目做**内容探针**
  （`HashCache.files_equal` 先比 size 再比哈希），抓「同尺寸不同内容」

**4. 传输强制 png+plist 成对**
`_expand_atlas_pairs`：勾任一文件自动补另一方。
理由：plist 描述 png 帧布局，缺一即渲染错乱。

**5. 变更时整对重传**
条目 `different` → png 和 plist 都标 different。多传几 KB 的 plist，
远比排查线上图集错位便宜。

### 踩坑记录（全部已修复并加回归测试）
1. `atlas` 节点 `absolute_path` 指向**文件本身**而非目录，
   早期当目录再拼文件名 → 产出 `xxx.png/xxx.png` 不存在路径 → **大小恒为0、传输全失败**
2. `action_diff_panel.py` 只 import 了 `PurePosixPath`，用了未导入的 `Path` → NameError 崩溃
3. 缺 png 时锚点落到 plist，PIL 去读 plist → `UnidentifiedImageError`
4. `CompareService`/`ActionDiffService` 只认 `sequence` 类型 → 图集条目数为 0
5. 冗余扫描工具对平铺图集目录返回 0 条（安全，不会误删，已加隔离测试）

### 验收结果（真实数据 local-role）
```

[对比] 1.5s | 条目 6746 | {'only_left': 6566, 'different': 3, 'same': 177}
[罗盘] ['E','N','NW','S','SE']

  ☑ | different  | 501031001/shadow | idle      |  12.1KB
```

- 方向罗盘、动作按钮、搜索（角色ID/部件）全部正常
- 传输 13138 个文件 0 失败

## 修复：用户实机反馈「扫描很慢，差异清单不出来」

### 现象
来源 `D:\GitWork\MiaoSpritesPackage\local-role`（1.4 GB）
目标 `E:\XYJProject\美术资源\动画序列帧\local-role`（**2.8 GB / 13826 文件**）
→ 界面停在「正在扫描并对比目录…」，差异清单空白。

### 根因 1：崩溃（清单不出来的直接原因）
`_collect_atlas_file_diffs` 在 `source_node is None`（目标独有条目）时
`return []`，但调用方按 `(list, bool)` 解包 → `ValueError`。
目标侧有 167 个目标独有条目，必然触发。异常在 worker 里被吞掉，
UI 永远等不到 `finished` 信号。

修复：`return [], False`。已加回归测试 `test_target_only_entry_does_not_crash`。

### 根因 2：性能（36 秒）
上一轮加的「内容探针」对 **6608 个已一致条目**逐个读全量文件，
= 读 4.2 GB，E 盘机械盘 → 35.1 秒。

**修复方案（重要取舍）**：
- 默认 `deep_verify=False`：字节数相同即判一致，**不读文件内容**
- `deep_verify=True` 时才做「字节数 → 采样指纹(头尾各4KB) → 完整哈希」三级校验
- `utils/hash_utils.py` 新增 `fingerprint_file` / `fingerprints_equal`，
  HashCache 增加 `_fingerprint_cache`

**理由**：打包产物重新出图时字节数几乎必然变化，字节数判定在实践中够用。
极限精度按需开启，不该让默认路径付出 30 秒代价。

### 真实目录实测（修复后）
```
【全链路】1.68s  条目 6913  {'same': 6608, 'different': 138, 'only_right': 167}
方向罗盘: ['E','N','NW','S','SE']
待更新 138 条，例如：
  ☑ | different | 502001    | attack | 288.2KB
  ☑ | different | 504004    | idle   |   5.1KB
```
refresh 1.0s + build_actions 0.69s。**36 秒 → 1.7 秒。**

### 教训（跨项目最佳实践）
1. 返回元组的函数，**所有 return 分支都要改** —— 单个 `return []` 漏改就是运行时崩溃
2. 「为了准确性加的兜底校验」必须**默认可关闭**。放在默认路径上，
   在 GB 级目录 + 机械盘场景会放大成几十秒。
3. 判定优先级：字节数（零读盘）→ 采样指纹（8KB）→ 完整哈希（全量），
   成本递增，逐级降级。
4. 性能优化不能只看单侧目录 —— 我最初只在 D 盘 SSD 上测，
   换到 E 盘 2.8 GB 目标目录才暴露问题。**验收必须用用户的真实两侧路径。**

## 修复 2：用户第二次反馈「还是卡住」（标题栏显示未响应）

### 现象
扫描已完成（状态栏显示「138 个动作待更新 · 276 个文件」），
但整个窗口「未响应」，差异清单空白。**UI 线程被卡死，不是扫描慢。**

### 定位方法
用 `QT_QPA_PLATFORM=offscreen` 写探针脚本，逐段计时：
```
扫描+构建 1.81s | 6913 条目
populate 1.85s
重建按钮 8.78s   ← 元凶
```

### 根因：动作快捷按钮爆炸 + O(n²) 同步
`_rebuild_action_buttons` 按 `action.action_name` 去重生成按钮。
图集条目的 action_name 是**完整文件名**（6913 个互不相同），
于是生成了几千个 QPushButton。

更糟的是 `_sync_action_buttons` 对每个按钮都遍历全部 6913 个动作，
退化成 O(按钮数 × 条目数)。

### 修复
1. `_action_label()`：按钮名改用图集解析出的动作名（idle/ride_run/attack…），
   数量恒定在个位数；非图集条目退回原 action_name
2. 加 `_MAX_ACTION_BUTTONS = 24` 上限保护，防未来再爆炸
3. `_sync_action_buttons` / `_sync_direction_buttons` 改为**单次遍历**
   预计算 totals/selected 字典，O(按钮数 + 条目数)

### 修复后（真实目录 + 应用级 e2e）
```
refresh_compare 返回 0.00s（异步）
状态栏：扫描完成 · 138 个动作待更新 · 276 个文件
面板行数 6913 / 可见 138 / 方向按钮 5 / 动作按钮 10
select_changed 0.03s
切筛选 0.03~0.04s
搜索 502001/501031001/shadow 0.04~0.05s
selected_summary 0.00s
```
按钮重建 8.78s → **0.02s**，populate 1.85s → 0.41s。

### 教训（跨项目最佳实践，很重要）
1. **「按名称去重生成控件」是危险模式**。当名称来源从「目录名」变成
   「文件名」时，去重基数从个位数暴涨到几千。控件数量必须设硬上限。
2. **同步类方法要防 O(n²)**。「每个控件都全量遍历数据」在数据量小时
   看不出来，上千条就崩。正确做法是单次遍历建字典。
3. **界面卡死要看标题栏「未响应」**：这比「慢」更严重，说明主线程阻塞。
   先分段计时定位，别盲目优化扫描。
4. 无头环境测试 UI：`QT_QPA_PLATFORM=offscreen` + `QApplication`，
   可以在 CI/命令行里跑真实 Qt 链路并计时。
5. **两轮性能问题的共同教训**：我只在 D 盘 SSD + 空目标目录上验证，
   用户真实环境是 E 盘机械盘 + 2.8 GB 目标目录 + 6913 条目。
   **验收必须构造与用户一致的规模**。

### 测试
`106 passed`（67 原有 + 39 新增）。新增 `AtlasUiScalingTests`
4 个用例锁住按钮爆炸与 O(n²)。
